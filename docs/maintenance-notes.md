# v2.1.9 维护经验

记录于 2026-10-06。对照的本地版本为主线 `606c19b` 和本仓库 `fc24b31`；后续版本应重新核对具体文件与行为。

## 两条路线怎么做

主线 [Tom6814/JMComic3-APK-NO-Ads](https://github.com/Tom6814/JMComic3-APK-NO-Ads) 把修改后的 APK 解包文件放进仓库。`main` 是去广告版，`no-games-no-movies` 是再去掉游戏和电影的版本；[打包工作流](https://github.com/Tom6814/JMComic3-APK-NO-Ads/blob/main/.github/workflows/build-release-apk.yml) 从两个分支取文件，重新打包、对齐、签名。这样可以直接审查交付文件，但每次升级都要核对大量二进制资源和混淆代码，也要处理大小写冲突的资源路径（主线为此增加了 `res_extra`）。

本仓库以官方 v2.1.9 APK 为输入，用 [`scripts/mod_apk.py`](../scripts/mod_apk.py) 自动解包、匹配并替换广告和板块代码，再打包签名。广告处理包括短路 Module 8038、清空 `first_links` 和弹窗数据；另有 [`scripts/test_mod_apk.py`](../scripts/test_mod_apk.py) 的补丁回归检查、`node --check` 和 [`scripts/local_ci.py`](../scripts/local_ci.py) 的模拟器检查。这让一次升级的补丁步骤可重跑，但规则依赖混淆代码的形状、模块编号和文件名；上游 APK 一变，必须先验证匹配范围，不能把旧脚本直接用于新版本。

两边都在 v2.1.9 上工作，区别是**版本化的解包结果**与**从原包重建的补丁流程**。主线更适合作为唯一面向用户的版本和问题入口；本仓库的脚本、断言和模拟器检查可作为后续主线升级的候选工具，按主线贡献指南拆成单一目的的改动再引入。

## 下次升级时的检查顺序

1. 记录官方 APK 的版本和校验值，保留未经修改的输入包；先确认主线已有的变体和对应版本。
2. 对比新版 Webpack chunk 和资源清单。逐个确认广告渲染、文字链接、开屏状态流、弹窗返回结构、游戏/电影入口；不要只看旧模块号或匹配次数。
3. 把每项修改限在可说明的行为上。开屏跳过广告仍需继续调用 `onNext()`；弹窗清空时保持调用方预期的数据形状；不要误动登录、Cookie、阅读器和暗色模式。
4. 在实际输入包上运行补丁断言和 JavaScript 语法检查，再核对打包内容。`resources.arsc` 必须保持未压缩；检查重名但大小写不同的资源、zipalign 和签名。
5. 安装成品，验证冷启动、年龄确认、首页、详情页、阅读器、暗色模式与两个变体。静态检查不能代替运行验证。
6. 给主线提交时遵守 [`CONTRIBUTING.md`](https://github.com/Tom6814/JMComic3-APK-NO-Ads/blob/main/CONTRIBUTING.md)：先沟通问题、一个 PR 一件事、不要格式化混淆文件，并附上真机或模拟器验证结果。主线文件补丁和生成脚本若同时改动，要能说明二者如何对应。

## 从当前 PR 得到的提醒

[主线 PR #17](https://github.com/Tom6814/JMComic3-APK-NO-Ads/pull/17) 在 service worker 里加入浏览器本地的并发计数。它会在超过阈值时直接拒绝请求，触发离线页或图片回退，即使网络正常。浏览器侧限制也不能代替服务端的流量控制。以后看到以安全问题为由修改 APK 前端时，先明确威胁发生在哪个信任边界，再检验正常用户路径和退化行为；不要仅凭 CWE 标题判断修补有效。
